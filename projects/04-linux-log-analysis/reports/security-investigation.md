# Linux SSH Authentication Security Investigation

## 1. Investigation Overview

This investigation examined SSH authentication activity on an Ubuntu
24.04.3 LTS laboratory system.

The objective was to identify failed and successful SSH authentication
events, extract relevant evidence, correlate related events, and
determine whether repeated authentication failures represented
malicious activity.

## 2. Environment

- Operating System: Ubuntu 24.04.3 LTS
- SSH Implementation: OpenSSH
- SSH Port: 22
- Investigated Log: `/var/log/auth.log`
- Laboratory Account: `vboxuser`

## 3. Initial Environment Assessment

The SSH server was initially not installed.

The following checks confirmed that SSH was unavailable:

```bash
sudo systemctl status ssh
ss -tulpn | grep :22
ps aux | grep '[s]shd'
```

## 4. Authentication Testing

A controlled successful SSH connection was performed using:

`ssh vboxuser@localhost`

The resulting log showed:

`Accepted password for vboxuser from ::1`

A controlled failed authentication attempt was then generated.

The log recorded:

`Failed password for vboxuser from ::1`

Additional controlled failures were generated to demonstrate
repeated authentication activity.

## 5. Evidence Collection

The following command was used to identify genuine SSH failed
authentication events:

`sudo grep -E 'sshd\[[0-9]+\]: Failed password' /var/log/auth.log`

The username, source address, and source port were extracted using:

`sudo grep -E 'sshd\[[0-9]+\]: Failed password' /var/log/auth.log |
awk '{print $1, $7, $9, $11}'`

Failed authentication attempts were also grouped by source address:

`sudo grep -E 'sshd\[[0-9]+\]: Failed password' /var/log/auth.log |
awk '{print $9}' | sort | uniq -c`

Result:

`6 ::1`

Failed attempts were grouped by username:

`sudo grep -E 'sshd\[[0-9]+\]: Failed password' /var/log/auth.log |
awk '{print $7}' | sort | uniq -c`

Result:
`6 vboxuser`

## 6. Findings

Six failed SSH authentication events were identified.

All events:

Targeted vboxuser
Originated from ::1
Occurred between 22:51:04 and 23:48:14
Were generated during the controlled laboratory exercise

The activity included short clusters of failed attempts, including
two failures within five seconds and another two failures within
eight seconds.

## 7. Successful Authentication Correlation

A successful SSH authentication was observed approximately 28 seconds
after the first failed authentication attempt.

The failed authentication occurred at:

`2026-08-12T22:51:04.451874+00:00`

The successful authentication occurred at:

`2026-08-12T22:51:32.219800+00:00`

Both events involved:

- User: `vboxuser`
- Source: `::1`
- Source port: `35916`

The matching username, source address, and source port strongly
support that the events were related to the same controlled SSH
connection activity.

Because the activity was intentionally generated during the
laboratory exercise, it was assessed as benign.

## 8. False Positive Investigation

Initial searches using:

grep "Failed password"

returned unrelated sudo log entries because the phrase appeared
inside previously executed grep commands.

A more precise regular expression was therefore used:

sshd\[[0-9]+\]: Failed password

This eliminated the observed false positives and isolated genuine
SSH authentication events.

## 9. Assessment

The observed authentication failures are classified as benign
laboratory activity.

Although repeated failed SSH authentication can be an indicator of
brute-force activity in a real environment, the evidence in this
exercise does not represent an actual attack because the events were
intentionally generated by the investigator.

## 10. Lessons Learned

This investigation demonstrated:

- How Linux authentication logs record SSH activity.
- How to distinguish genuine events from false positives.
- How to use grep and regular expressions for log filtering.
- How to use awk to extract security-relevant fields.
- How to use sort and uniq to count repeated events.
- How to correlate authentication events using timestamps,
  usernames, source addresses, and source ports.
- Why evidence must be interpreted within its context.
- Why repeated authentication failures should not automatically
  be classified as malicious activity without additional evidence.
