# Linux Incident Response Lab

## Project Overview

This project demonstrates a controlled Linux incident response investigation
using an Ubuntu virtual machine.

A simulated persistence mechanism was introduced through a malicious-looking
cron job. The investigation followed a basic incident response workflow:

**Detection → Investigation → Evidence Preservation → Containment → Eradication → Recovery**

---

## Scenario

A suspicious cron job named `security-update` was discovered under:

`/etc/cron.d/`

The scheduled task was configured to execute every five minutes as `root` and
write a simulated security event to:

`/var/log/security-lab.log`

The activity was intentionally created for this lab and does not represent a
real compromise.

---

## Investigation

The following areas were investigated:

- Cron configuration
- Cron service status
- Cron execution logs
- System journal entries
- File ownership and permissions
- File timestamps and metadata
- Generated log activity
- Existing scheduled tasks

The suspicious cron job was confirmed to be executing with root privileges.

---

## Evidence Preservation

Before removal, the suspicious cron configuration was preserved as:

`evidence/security-update.evidence`

Additional evidence and investigation notes are stored in the `evidence/`
and `notes/` directories.

---

## Containment and Eradication

The suspicious cron job was removed from the live system after evidence
preservation.

Legitimate cron entries were left unchanged.

Additional searches confirmed that no remaining references to the simulated
persistence mechanism remained in the live cron configuration.

---

## Recovery

The cron service remained active after containment.

Post-containment verification confirmed that the simulated event was no longer
being generated by the removed cron job.

The historical `security-lab.log` was retained as evidence.
